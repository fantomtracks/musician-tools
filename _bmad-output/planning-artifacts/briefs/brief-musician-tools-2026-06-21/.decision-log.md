## 2026-06-21 — Menace #1 (Account takeover) : décisions

- **Modèle de menace** : northwood traite les **4 menaces à fond** (« propre une bonne fois ») — takeover, IDOR/ownership, CSRF, énumération.
- **C1 — Politique mot de passe** : **minimum 10 caractères**, pas de règles de composition, pas de rotation forcée (NIST-moderne). ✅
- **C2 — Invalidation de session** : au changement de mot de passe, **détruire toutes les autres sessions** du user (garder la courante). Via le store Postgres `connect-pg-simple`. ✅
- **C3 — Changement d'email = VÉRIFICATION (C3-b)** : on bascule l'email **seulement après confirmation de possession** (lien). ⚠️ **Implique de monter une infra d'email transactionnel** (nouvelle dépendance, absente aujourd'hui). northwood : « on fait l'email, let's go ». ✅
- **C4 — Rate-limiting** : ajouter `express-rate-limit` sur `/login` + change-password (anti-brute-force). ✅
- Faits de code : cookie déjà `httpOnly` + `secure`(prod) + `sameSite:lax` ; `GET /auth/logout` = state-changing GET (angle CSRF résiduel de Lax) ; pas d'infra email ; JWT/`jwt` importé mais non utilisé dans `authsess.js`.

## 2026-06-21 — Périmètre email étendu : E3 (tout)

- **E3 tranché** : l'infra email couvre les TROIS usages — (1) change-email vérifié, (2) **reset password par email**, (3) **vérification obligatoire à l'inscription**. northwood : « propre une bonne fois ».
- Conséquence : l'Epic 7 passe de « éditer mon profil » à **« gestion de compte complète »** (profil + reset + vérif inscription). Touche le flux d'inscription existant (ajoute de la friction).
- **Open question (à trancher plus tard, pas bloquant le brief)** : que peut faire un user **non vérifié** ? (a) gate dur = pas d'accès tant que non vérifié ; (b) soft = connecté mais limité/relancé. Façonne l'UX du signup.

## 2026-06-21 — Menace #2 (IDOR / ownership) : décisions

- Audit du code : le pattern canonique `401→404→403` est suivi **quasi partout** (instruments, playlists, sessions, topics, songlinks, et `markSongPlayed` vérifie l'ownership de la *chanson*). Bonne surprise.
- Vrais trous : **`getSong` (`songcontroller.js:78-89`)** = seul vrai IDOR (aucun ownership) ; **`markSongPlayed`** ne valide pas que l'`instrumentUid` appartient au user (mineur).
- **D-audit tranché (« 1 »)** : audit ownership **systématique** de toutes les routes + fix `getSong` + validation `instrumentUid`. ✅
- **403-vs-404 → COLLAPSE EN 404 PARTOUT** (tranché). Requêtes scopées `where: { uid, userUid }` → « pas à toi » indistinguable de « n'existe pas ». Supprime l'oracle d'énumération (volet IDOR de la menace #4) et simplifie le code. ✅

## 2026-06-21 — Menace #3 (CSRF) + hygiène auth : décisions

- **Nettoyage tranché (« 1 OK »)** : `logout` GET → **POST** (+ vérifier qu'aucune route mutante n'est en GET) ; **retrait du JWT mort** (émis jamais vérifié ; import `jwt` inutile dans `authsess.js`) ; **secret obligatoire** au démarrage (échec si `JWT_SECRET`/`SESSION_SECRET` absent, plus de fallback `'MUSICIAN_SECRET'`). ✅
- **CSRF = option c (token), « à fond »** tranché par northwood. Token CSRF en plus de SameSite=Lax. Reco mécanique (→ addendum) : **synchronizer token stocké en session** (store Postgres déjà présent) plutôt que double-submit cookie. À confirmer en archi. ✅

## 2026-06-21 — Menace #4 (énumération) + virage email-only : décisions

- **Email généricisé** (tranché) : plus jamais « email pris ». Register répond toujours « vérifie ta boîte » ; si l'email existe, **notifier le vrai propriétaire** au lieu de créer un doublon. Gratuit grâce à l'infra email (E3). ✅
- **LOGIN EMAIL-ONLY** (tranché, « let's go ») : on supprime le username comme identifiant de connexion.
  Ripples :
  - `loginUser` : lookup **par email seul** (retirer le `Op.or` name/email iLike).
  - `name` devient un **nom d'affichage** : **plus unique**, éditable librement (drop de la contrainte unique sur `Users.name` via migration). Supprime de fait toute fuite d'énumération sur le username.
  - **Email normalisé** (lowercase + trim) et **unique insensible à la casse** (`citext`/`LOWER()`), pour qu'`Email@x.com` == `email@x.com` = même compte. → traite le volet « casse/accents » de la dette là où il compte vraiment (l'email).
  - Migration : users beta existants ont tous un email (déjà requis/unique) → bascule à faible risque ; leurs `name` deviennent cosmétiques.
- **Menace #4 close** : volet IDOR par le 404 ; volet email par la généricisation ; volet username supprimé par l'email-only.

## 2026-06-21 — RÉVISION : identité Discord-style (handle name#discriminant)

- **Changement par rapport à la décision précédente** (« name = cosmétique non unique ») : northwood veut une **identité unique de type Discord** en vue d'un **futur partage de songlist**.
- **Modèle retenu** :
  - `email` reste l'**identifiant de connexion** (email-only inchangé).
  - `name` (nom d'affichage) = **non unique seul** (doublons permis).
  - **Discriminant `#NNNN`** (4 chiffres, ex. `#8590`) auto-assigné → **handle `name#NNNN` = identité unique et partageable**.
  - L'unicité DB passe sur la **paire (name, discriminant)** (ou une colonne `handle` calculée unique).
- **Conséquence énumération** : on ne **refuse jamais** un nom (auto-disambiguïsation) → plus de message « nom pris » → **oracle d'énumération du nom supprimé par construction** (mieux que « assumer le leak »). Généricisation email conservée.
- **Périmètre** : l'Epic 7 **pose le modèle d'identité** (name + discriminant + handle unique). Le **partage de songlist = épic futur** (hors 7).
- Sous-décisions à confirmer/archi : format discriminant (4 chiffres `0001`–`9999` ?) ; **stabilité du discriminant** quand on change de nom d'affichage (le garder si `(nouveau_nom, disc)` libre, sinon en réassigner un) ; collation : unicité du handle insensible à la casse cohérente avec l'email normalisé.
