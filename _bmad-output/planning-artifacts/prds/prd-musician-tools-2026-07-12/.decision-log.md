# Decision Log — PRD Catalog (musician-tools)

_Mémoire canonique + piste d'audit du run PRD Catalog. Chaque décision, changement et override est consigné ici au fil de la conversation._

## 2026-07-12 — Démarrage du run
- **Intent : Create** (aucun PRD Catalog existant). Espace de travail : `prd-musician-tools-2026-07-12/`.
- **Contexte-graine** : Catalog = pool **partagé** de chansons prêtes, pré-remplies, qu'on parcourt et copie dans sa **Songlist** perso (verbes _Browse catalog_ / _Add to my songlist_ ; vocab `CLAUDE.md`). Distinct de la Songlist (collection perso existante).
- **Provenance** : promu au backlog du PRD journal (`prd-musician-tools-2026-06-06`, § Exclu) le 2026-07-12 ; séquencé comme prochain gros chantier produit ; débloque la future landing page.
- **Contrainte structurelle notée** : app aujourd'hui **mono-user beta** (3-4 users) ; le Catalog introduit une notion **partagée/multi-user** → probable rupture de modèle à cadrer.

## 2026-07-12 — Calibrage enjeu
- **Stakes = « Refonte structurante »** (choix northwood) → PRD approfondi. Le Catalog force la bascule mono-user → multi-user et redéfinit le modèle chanson (canonique partagé vs copie perso). Rigueur/longueur du PRD calées en conséquence.

## 2026-07-12 — Recherche de paysage (subagent)
- Digest concurrentiel obtenu (Ultimate Guitar, MuseScore, Songsterr, Chordify, apps setlist, modèle Spotify). Points saillants :
  - **Décision cœur = sémantique de la copie** : snapshot/fork (UG "personal", MuseScore) vs lien-vivant (Spotify) vs **snapshot-avec-provenance** (copier les champs + `sourceCatalogId` + version → offrir « la source a changé, revoir »).
  - **Modèle deux-tiers** (UG) : favori/lien *et* copie perso éditable — les users veulent « suivre la source » ET « la rendre mienne ».
  - **Portée métadonnées seulement** (BPM/clé/mode/signature/accordages = faits, peu copyrightables) pour éviter le risque licence de MuseScore (tabs/partitions/paroles).
  - Identité canonique / dédup : pas d'ID universel ; titre+artiste collisionne (covers, live) → clé normalisée, éventuel MBID/ISRC ; flux « tu l'as déjà / existe au catalog » au moment du Add.
  - Seed : **curated d'abord** (toi) puis contribution communautaire plus tard (gouvernance/modération).
  - Garde-fou directionnel : copie **one-way** Catalog→Songlist ; jamais de write-back vers le pool partagé.

## 2026-07-12 — Décisions cadrage (brain dump northwood + reco)
- **Idée maîtresse = friction zéro** : le user ajoute à sa Songlist une chanson **déjà entièrement remplie** (BPM, liens YouTube/Spotify, métadonnées) au lieu de tout ressaisir.
- **DÉCISION — Sémantique de la copie = SNAPSHOT + PROVENANCE** (choix northwood, reco alignée). On copie les champs → chanson perso **éditable librement** ; on stocke `sourceCatalogUid` + version (invisible). **v1 = simple copie**, aucune UX de mise à jour. Increment ultérieur possible : « la fiche Catalog a changé → revoir/appliquer ? » (proposée, jamais silencieuse). Rejeté : lien-vivant pur (conflit avec l'édition + couplage dur aux logs/playlists/lastPlayed perso) et snapshot-pur-sans-provenance (fermerait la porte au « mettre à jour » sans re-migration). Réglages perso (accordage, difficulté, notes, historique) jamais écrasés.
- **DÉCISION — Portée contenu v1 = MÉTADONNÉES + LIENS OFFICIELS uniquement** (BPM, clé, mode, signature, accordages, instruments, difficulté, liens YouTube/Spotify). **Paroles et tabs/accords HORS v1.** Contre-pied acté : les **paroles** sont juridiquement **les plus risquées** (contenu protégé, licences Musixmatch/LyricFind payantes), pas l'inverse ; si un jour → fournisseur licencié ou champ **perso** (pas dans le pool partagé). Tabs/accords = double risque (copyright + « personne n'est d'accord » → versions multiples/notation/modération lourde).
- **FEATURE — Collections Catalog curées** (« Rock 90 », « Pop 2000 »…) : bundles curés côté Catalog qu'un user **enregistre/importe d'un coup** dans sa Songlist. Miroir partagé des **Playlists** perso existantes. À inclure au PRD (possiblement phase ultérieure).
- **CONTRIBUTION** : les users pourront contribuer **un jour** (pas v1). v1 = **seed curé par northwood**. Le modèle (provenance, ownership d'une entrée Catalog, statut de publication) ne doit pas fermer la porte à la contribution.

## 2026-07-12 — Décisions cadrage (salve Fast path)
- **DÉCISION — Identité = une entrée canonique par chanson** (clé titre+artiste normalisée, miroir de l'index unique perso Epic 17). Pas de variantes/versions groupées en v1 (accordages/clés alternatifs = champs, pas entrées séparées). Variantes = évolution future si besoin.
- **DÉCISION — Visibilité v1 = connectés seulement.** Parcourir le Catalog exige d'être loggué (cohérent avec l'app, aucune surface publique à sécuriser). La landing page montrera des captures. **Browse public = increment ultérieur** (surface SEO/rate-limit/cache à cadrer alors).
- **DÉCISION — Seed v1 = mini-UI admin/curateur.** Introduit un **rôle curateur** + écran admin protégé pour créer/éditer les entrées Catalog et composer les collections. Réutilisable à l'ouverture de la contribution. Rejeté : seed par scripts/SQL seul (intenable pour un catalogue + collections qui grossissent). ⚠️ 1ᵉʳ rôle/notion d'autorisation au-delà de l'ownership — nouvelle brique sécu.
- **DÉCISION — Add d'une chanson déjà dans ma Songlist = bloquer + pointer l'existante.** Réutilise la garde doublon per-user (titre+artiste, Epic 17 / 409). Pas de copie en double (préserve l'invariant d'unicité).
- **ASSUMPTIONS par défaut (Fast path, à confirmer en review)** : (a) modèle = nouvelle table `CatalogSong` partagée sans `userUid`, distincte de `Song` perso ; le Add crée une `Song` perso depuis une `CatalogSong` + `sourceCatalogUid` ; (b) surface = même SPA web React responsive ; (c) auto-fill SongBPM réutilisable pour seeder ; (d) métriques proposées (part d'ajouts via Catalog, time-to-first-song) ; (e) contribution = phase future décrite, non construite.

## 2026-07-12 — Validation (Reviewer Gate) + Update : 5 points tranchés
- **Contexte** : validation du draft (rubric walker `strong`/`adequate` sur 7 dimensions ; passe adversariale → 3 « CRITICAL » + 5 HIGH). Vérification code (`backend/models/song.js`) → recalibrage : les colonnes existent déjà dans `Song` (pas de migration ni de perte de données) ; les CRITICAL adversariaux deviennent HIGH/MEDIUM. Grade **Fair** (`validation-report.html`). northwood a demandé un Update pour trancher les 5 points bloquants avant les epics.
- **DÉCISION 1 — Mapping Catalog→Song = parité de colonnes.** `CatalogSong` calque les **noms/formes de colonnes de `Song`** (`instrument`, `instrumentDifficulty`, `instrumentTuning`, `streamingLinks` JSONB, etc.) → la copie `Add` est un **quasi-1:1** sans couche de transformation. Rejeté : noms « Catalog propres » + tableau de mapping (couche de transform à maintenir/tester). Ferme Q ouverte §8.5. [FR-4, addendum, §9]
- **DÉCISION 2 — Identité canonique + uid stable par contrat.** Une entrée canonique par (titre+artiste), **variant-hostile assumé** en v1 (studio/live/drop-D ≠ entrées distinctes ; variantes = v2 = changer la clé unique). L'index unique est **global** (pas per-user comme Epic 17 — faux-ami explicité). **Correction = `UPDATE` in-place, uid stable garanti, jamais delete+recreate** d'une fiche référencée → la provenance ne pend pas. Résout C2 (framing global) + C3 (fragilité provenance). Rejeté : discriminant de variante dès v1 (scope). [FR-11, FR-13, §5, NFR-4, addendum]
- **DÉCISION 3 — Autorisation admin = 403 franc + booléen `isCurator`.** Refus des routes d'écriture Catalog = **403** (pas 404). Raison : le Catalog est **lisible par tout connecté** → l'écriture n'a aucun secret d'énumération à protéger ; le pattern 404 anti-oracle 7.5 (cacher les ressources d'autrui) ne s'applique pas. Rôle = attribut booléen `isCurator` sur User (pas de table de rôles). northwood avait d'abord penché 404 (uniformité) puis basculé sur la reco 403 après argumentaire. Ferme Q ouverte §8.3. Exception à inscrire dans `project-context.md`. [FR-10, NFR-3, addendum]
- **DÉCISION 4 — Import de Collection = Playlist perso miroir.** L'import crée (ou réutilise, unicité `lower(name)` Epic 10) une **Playlist perso du nom de la Collection** et y rattache toutes les chansons du lot → tient la promesse d'UJ-2 (« monter un répertoire »), résout H4. Réutilise la brique Playlist (Epic 10) + FK `playlist_songs` (5.7). Import best-effort + idempotent, récap `{added, skipped, failed}`. Sort du non-goal §6.2 → **MVP** (≈ +1 story). Ferme Q ouverte §8.6. [FR-9, §4.3, §6.1, addendum]
- **DÉCISION 5 — SM-1 refondue directionnelle + seed cible.** SM-1 devient une **métrique directionnelle** (tendance à la hausse), **sans seuil chiffré** (« >50 % » retiré : fausse rigueur à N≈4). Option **B retenue** (northwood) : les imports de Collection restent **comptés dans SM-1** (pas de métrique séparée) — SM-C1 (« copiées jamais jouées ») garde déjà contre le remplissage vide. Définition de « seedé » = **cible ~50–100 fiches + 3–5 Collections** au lancement (SM-4). Résout H2/H3. Ferme Q ouverte §8.4. [§7 SM-1/SM-4]

## 2026-07-12 — Ajout feature future : popularité / analytics du Catalog
- **Demande northwood** : connaître la popularité des fiches (adds + plays agrégés sur tous les users) pour prioriser la curation et monter des Collections « Top N » (ex. « Top 10 RHCP »), éventuellement trier le browse par popularité.
- **DÉCISION — Capturé comme increment futur MODÈLE-AWARE, non construit en v1** (§4.7). Raisons : (a) **déjà calculable sans migration** grâce à la Provenance `sourceCatalogUid` (adds = Songs pointant la fiche ; plays = SongPlays de ces Songs, provenance survivant à l'édition) → agrégation en lecture, ajoutable plus tard ; (b) **valeur = échelle** : bruit à N≈4 (même logique que le retrait du seuil SM-1) ; (c) **nouveau flux perso → partagé** (1ʳᵉ fois que la donnée perso alimente le pool commun) → sécu/vie privée à cadrer, **seuil anti-dé-anonymisation** requis pour tout affichage user-facing, **curateur-only** comme point d'entrée le moins sensible ; (d) Collections « Top N » restent **curées à la main** (FR-12), la popularité informe mais ne génère pas. Rejeté (pour l'instant) : petite vue popularité curateur-only dès la v1 (repoussé, pas prioritaire vs le socle Catalog). Renforce le rôle de la Provenance (glossaire §3, §4.5+§4.7).
