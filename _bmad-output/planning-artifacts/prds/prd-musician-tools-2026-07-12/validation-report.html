La passe adversariale déplace nettement le tableau. Sous une forme propre, plusieurs décisions fondatrices sont présentées comme acquises alors qu'elles sont en réalité des questions ouvertes bloquantes : le mapping champ-par-champ Catalog→Song (FR-4), la stabilité de l'uid canonique dont dépend toute la provenance, et le choix 403-vs-404 sur l'admin (décision de sécu conceptuelle, pas d'implémentation). Elle relève aussi des métriques dimensionnées pour une échelle que le produit n'a pas (N≈4) et une promesse UX Collections qui s'évapore à l'import.

Note du validateur (vérification code). J'ai recalibré les 3 CRITICAL de l'adversarial après lecture du modèle Song réel. Bonne nouvelle sur C1 : les colonnes existent déjà (genre/language en JSONB, timeSignature, mode, durationSeconds, key, album) — aucune migration de la table Song perso, aucune perte silencieuse de données ; la framing « data-loss » est surestimée. Net : les « CRITICAL » deviennent des HIGH/MEDIUM à trancher avant les epics, aucun n'est un défaut bloquant-cassé. D'où la note Fair : de bonnes fondations, mais un socle qui repose sur des décisions non prises.

critical → [high]

C1 — Mapping de champs Catalog→Song non figé

FR-4 · §8.5 · addendum
FR-4 « crée une Song à partir des champs de la fiche » mais le mapping champ-par-champ est une question ouverte. Recalibrage validateur : les colonnes existent dans Song (pas de migration ni de perte de données) — mais les noms/formes divergent (instrumentTypes≠instrument, difficulty≠instrumentDifficulty, tunings≠instrumentTuning, youtubeUrl/spotifyUrl vs streamingLinks JSONB). Sémantique difficulty : Catalog = suggérée/objective vs perso instrumentDifficulty = par-instrument.
Fix : figer un tableau de correspondance champ-par-champ (nom source → nom cible → transformation de forme) en architecture — pré-requis de FR-4/FR-9. Aligner aussi le nommage CatalogSong de l'addendum sur Song pour tuer l'illusion d'une copie 1:1.
critical → [high]

C2 — Identité canonique globale variant-hostile, sans workflow de correction

FR-13 · §4.4 · §6.2 · addendum
« Miroir de l'index Epic 17 » est un abus de langage : Epic 17 est per-user (tu corriges ta ligne), l'index Catalog est global (la 1ʳᵉ fiche verrouille la clé pour tous). Le curateur ne peut pas seeder studio vs live, standard vs drop-D (mêmes titre+artiste). Passer aux variantes en v2 exigera de changer la clé unique — migration sur donnée partagée en prod. Le besoin émerge à « la chanson n°2 qui est une reprise ».
Fix : assumer explicitement en architecture le choix v1 « une entrée canonique » + décrire un workflow de correction/merge, ou introduire dès v1 un discriminant de variante dans la clé.
critical → [medium]

C3 — Provenance fragile dès qu'un curateur corrige un titre

§4.5 · NFR-4 · addendum
Snapshot +provenance (vs snapshot pur) n'est justifié que par le futur re-sync (§4.5). Si corriger une fiche se fait par delete+recreate → nouvel uid → tous les sourceCatalogUid distribués pendent en silence. Recalibrage validateur : partiellement réfutable — une édition in-place (UPDATE même ligne) préserve l'uid ; le delete+recreate n'est pas forcé. Le risque tient uniquement si la curation supprime-recrée.
Fix : poser par contrat « édition in-place, uid stable, jamais delete+recreate une fiche référencée » ; sinon assumer que la provenance est best-effort et cesser d'en faire la raison d'être du snapshot.
high

H1 — Anti-oracle 403/404 cargo-culté sur l'admin Catalog

FR-10 · addendum §Autorisation
Le pattern 7.5 cache les ressources d'autrui ; le Catalog est publiquement lisible par tout connecté — il n'y a rien à cacher. 404 sur la route d'écriture d'une ressource déjà lisible = théâtre. Le bon choix est un 403 franc. C'est une décision de sécu conceptuelle, pas d'implémentation : elle conditionne requireCurator, chaque route d'écriture et les AC.
Fix : trancher 403 en amont (architecture) et purger la « Consequence testable » indécise de FR-10.
high

H2 — SM-1 mesure la couverture déguisée en adoption, gonflable par imports batch

§7 · SM-1
Coverage ≠ adoption : catalogue maigre → saisie manuelle → SM-1 bas (pénalise un bon produit). Et 1 import de Collection = 20 « adds Catalog » d'un clic → franchit >50 % trivialement, récompensant le remplissage vide que SM-C1 dénonce.
Fix : découpler adoption/couverture ; exclure (ou compter à part) les adds issus d'imports batch ; qualifier « une fois seedé » par un volume de seed décidé.
high

H4 — La valeur des Collections s'évapore à l'import

§4.3 · FR-9 · UJ-2 · §8.6
FR-9 assume que l'import ne crée pas de Playlist perso → après « Rock 90 » (20 titres) le user obtient 20 chansons en vrac sans regroupement thématique. Le JTBD émotionnel et le climax d'UJ-2 promettent une cohérence que le résultat ne livre pas. Le mapping Collection→Playlist est relégué en v2.
Fix : trancher Collection→regroupement perso avant de figer FR-9 (UX), sinon la feature phare de §4.3 est un anti-climax.
high

H3 — Goulot « un seul curateur » + volume de seed indécis

UJ-3 · §8.4 · SM-1/SM-4
Tout le catalogue dépend d'une personne saisissant les fiches une par une ; le volume de seed est une question ouverte ; le CSV import (seul levier réaliste) est repoussé. « Une fois seedé » (SM-1) n'a donc pas de définition, et SM-4 n'a ni cible ni capacité de production estimée.
Fix : décider le volume de seed cible et le pipeline (saisie/auto-fill/CSV) ; sans lui, SM-1/SM-4 sont bâties sur du sable.
high

H5 — La garde de doublon rate sur les données saisies avant le Catalog

FR-6 · FR-9
Les chansons déjà saisies à la main n'ont jamais transité par la normalisation canonique : « Zombie / Cranberries » (user) vs « Zombie / The Cranberries » (Catalog) → la garde ne matche pas → doublon quasi-identique en silence ; ou fusion agressive perçue comme un bug (SM-C2). Le récap « 18 added, 2 already » peut être faux dans les deux sens.
Fix : spécifier la normalisation exacte et le comportement sur collisions partielles/near-miss.
